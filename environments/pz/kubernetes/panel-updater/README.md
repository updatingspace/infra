# Автоматическое обновление панели

На 30 сентября 2026 расписание **включено** (`suspend=false`). Первое
обновление 1.3.7 → **1.4.0** выполнено с полной проверенной копией данных;
журнал `committed`, версия и статус Up to date подтверждены в браузере.
Идентичность игрового pod/контейнера и число рестартов сохранились, RCON
проверен до и после. Повторный Job завершился `no_change / already_current`.

`updater.py` обновляет только Deployment `panel` в namespace `zomboid`.
Terraform создаёт CronJob `panel-auto-update`: запуск каждый час на 17-й минуте
UTC, `concurrencyPolicy = Forbid`, лимит Job — 900 секунд. Скрипт использует
до 600 секунд на обновление и отдельные 240 секунд на откат. На игровой VM
нет сборки образов; Docker socket не используется.

Источник версии — последний стабильный GitHub release
[`fpsacha/zomboid-control-panel`](https://github.com/fpsacha/zomboid-control-panel/releases).
Разрешены только теги `vX.Y.Z`, без prerelease, draft и понижения версии.
Скрипт получает официальный `ghcr.io/fpsacha/zomboid-panel:X.Y.Z`, проверяет
SHA256 index, дочернего manifest linux/amd64 и image config, а также совпадение
OCI version/revision/source с релизом и commit его Git-тега. В Deployment
записывается `tag@sha256:...` с `IfNotPresent`. `latest` и `main` не используются:
upstream [публикует их из main](https://github.com/fpsacha/zomboid-control-panel/blob/v1.4.0/.github/workflows/docker-publish.yml).

## Порядок обновления

1. Проверить текущую Ready-панель, её версию и владение pod через ReplicaSet
   и UID Deployment. Отказаться при незавершённом журнале, ранее неудачной
   версии/digest, недостатке места или недоступных файлах.
2. Захватить файловую блокировку и записать журнал. Остановить только панель
   через `replicas = 0`; дождаться полного исчезновения её pod.
3. Скопировать `/panel-data`, исключая служебный каталог updater. Сохранить
   права и времена файлов, выполнить fsync и повторно прочитать каждый файл
   backup с проверкой SHA256 до запуска новой версии.
4. Запустить новую панель с отдельной меткой
   `pz.updspace.com/release-slot`. Service пока выбирает прежнюю метку,
   поэтому пользовательский трафик не поступает в непроверенную версию.
5. Дождаться одной Ready-реплики нужного образа, проверить
   `http://<podIP>:3001/api/health`, точное совпадение версии и, при включённой
   телеметрии, маркер совместимости адаптера. Только затем
   переключить selector Service и завершить журнал фазой `committed`.

При `panel_telemetry_enabled=true` Terraform задаёт updater
`PANEL_TELEMETRY_REQUIRED=true`. Проверка health требует
`telemetry.adapter=kubernetes-game-v1`, `compatibility=verified` и
`scope=game-container-v1`: у прежней панели до остановки, у кандидата до
переключения трафика и у восстановленной панели при откате. Строгие проверки
[адаптера](../panel-telemetry/README.md) могут отклонить будущий upstream-образ;
успешное обновление до любой будущей версии заранее не гарантируется.
`telemetry.ready=false` из-за остановленной игры не блокирует обновление панели.
Запуск с уже установленной версией завершается `no_change` и не заменяет эту
проверку или постоянный мониторинг здоровья.

При подтверждённой ошибке до переключения трафика updater снова останавливает
панель и ждёт исчезновения всех её pod. Он проверяет backup, переносит данные
неудачной версии в закрытый служебный каталог, восстанавливает прежние данные
и образ, затем проверяет Ready и версию. Прежний локально импортированный образ
с `Never` разрешён для первого отката с официального образа. Если проверка
backup не прошла ещё до запуска кандидата, исходные данные не восстанавливаются
из повреждённой копии: запускается прежний образ на нетронутых данных.

Потерянный ответ PATCH, прерывание операции, попытка переключения Service с
неясным результатом или ошибка восстановления требуют оператора. В этих
случаях скрипт не повторяет изменение и не восстанавливает данные автоматически.
Журнал остаётся незавершённым. Возврат старого образа без восстановления данных
не считается полноценным откатом миграции базы.

## Данные и ограничения места

Единственный том данных updater — PVC `panel`, смонтированный в `/panel-data`.
Мир, игровые файлы и логи других сервисов ему не смонтированы. Служебные файлы
находятся в `/panel-data/.k8s-panel-updater` с режимом каталога `0700`:

- `journal.json` — текущая или последняя завершённая операция;
- `backups/<id>/` — проверенные снимки данных панели;
- `failed-data-<id>/` — сохранённые данные неудачной версии;
- `failed-digests.json` и `failed-versions.json` — запрет повторного запуска
  неудачного артефакта или той же версии с перепубликованным digest;
- `lock` — файл блокировки; его наличие само по себе не означает активный Job.

Исходные данные ограничены **1 ГиБ** и 20 000 записей. Снимок включает весь
каталог панели, в том числе `map-tiles-cache`; исключается только собственный
служебный каталог updater. Суммарный бюджет служебного каталога — **3 ГиБ**.
До остановки панели проверяется запас
для backup и сохранения данных при откате, включая округление до блоков и
метаданные. Дополнительно требуется не менее **512 МиБ свободного места плюс
размер снимка** на файловой системе. Те же ограничения проверяются повторно
перед копированием; сохранение неудачных данных отдельно проверяет бюджет.
Недоступные для чтения каталоги, символьные ссылки, специальные файлы,
hardlink и несовпадающий владелец/группа приводят к отказу.

Первый управляемый запуск остановился до изменения панели: её данные занимали
около 679 МБ, включая около 663 МБ кэша карт, и превышали исходный порог 256 МиБ.
Пороги увеличены для сохранения полного снимка без удаления или исключения кэша.
Копирование и проверка SHA256 остаются потоковыми; лимиты контейнера
100m CPU / 128 МиБ RAM не изменены. Эти бюджеты используют существующую
файловую систему namespace `zomboid` размером 26 ГиБ.

Автоматического удаления backup нет. Retention выполняется вручную после
проверки завершённых операций; при достижении бюджета updater откажется от
следующего обновления. Не удалять незавершённый журнал, нужный для восстановления
backup или данные неудачной версии до разбора операции. Проверка свободного
места и лимиты updater — ограничения этого процесса; это не отдельная файловая
система и не физическая quota каталога, защищающая от любого другого писателя.

## Запуск и Terraform

В контейнере доступны два режима:

```sh
python3 /opt/updater/updater.py --check-only
python3 /opt/updater/updater.py --once
```

`--check-only` только читает метаданные релиза, registry и текущего Deployment.
Он не создаёт каталог, lock или Job и не записывает в PVC/Kubernetes. Этот режим
не заменяет проверку места и полноценную приёмку обновления. `--once` — режим
по умолчанию. stdout содержит только безопасные статусы, фазы, версию и digest;
токены, ответы health, конфигурации и содержимое данных не выводятся.

Переменные: `POD_NAMESPACE=zomboid`, `INITIAL_VERSION=1.3.7`,
`UPDATE_TIMEOUT_SECONDS=600`, `ROLLBACK_TIMEOUT_SECONDS=240`. Используются
стандартные адрес API Kubernetes, service-account token и CA. Внешние учётные
данные не нужны. Контейнер запускается с UID/GID 1000.

Первый запуск расписания должен оставаться приостановленным:
`panel_updater_suspended = true`. На существующей панели сначала должны быть
одинаковые метки `release-slot=initial` в pod template и Service selector;
не изменять immutable selector Deployment. Проверить discovery, выполнить
первое управляемое обновление и подтвердить готовность панели и независимость
игры. **После успешной приёмки установить `panel_updater_suspended = false`**
в действующих Terraform variables и применить проверенный план. Наличие кода
или успешный `--check-only` не означает, что расписание уже включено.

Работать с workloads через `deploy.py`:

```sh
python3 environments/pz/kubernetes/deploy.py sync
python3 environments/pz/kubernetes/deploy.py plan workloads
python3 environments/pz/kubernetes/deploy.py apply workloads
```

Перед планом helper приостанавливает CronJob и ждёт отсутствия активных Jobs/Pods
и допустимого журнала: файл отсутствует либо фаза `committed`/`rolled_back`.
Он не останавливает выполняющийся updater. До запуска apply условия проверяются
ещё раз. Между plan и apply расписание остаётся приостановленным; применение
возвращает настроенное значение `panel_updater_suspended` после изменений
Deployment и Service. При отказе или брошенном плане расписание не возобновляется
само. Не обходить этот порядок параллельным Terraform apply или ручным Job.

Terraform управляет ресурсами, постоянным числом реплик и расписанием; image,
pull policy и метки переключения трафика принадлежат updater. Код адаптера,
его checksum, ServiceAccount, mounts, ресурсы и probes остаются под управлением
Terraform. Незавершённый
журнал блокирует новый update и workloads apply до ручной проверки. Удаление
журнала без восстановления согласованного состояния не является исправлением.

## Доверие и пределы проверки

ServiceAccount может читать и менять только Deployment `panel` и Service
`panel`; чтение pod/ReplicaSet доступно в namespace для проверки владельцев.
Нет прав на exec, Secret API или изменение игрового StatefulSet. Вместе с тем
право PATCH Deployment — значимое доверие: RBAC не ограничивает его отдельным
полем image, а pod templates могут ссылаться на ресурсы namespace. Поэтому
updater, его script ConfigMap и upstream-образ считаются доверенными компонентами;
это не абсолютная граница изоляции от скомпрометированного кода.

Токен updater отличается от токена панели: ServiceAccount `panel-telemetry`
панели разрешает только GET одного игрового Pod и его метрик, без операций
управления. Игре и Caddy ServiceAccount token не монтируется.

Проверка Ready, версии и совместимости адаптера подтверждает запуск панели,
но не все её функции и не наличие свежих игровых метрик.
Само обновление не добавляет upstream-панели Kubernetes lifecycle: управление
игрой через её Start/Stop/Restart требует отдельной адаптации. Штатный путь
остановки игрового StatefulSet остаётся отдельной операцией.

Локальная проверка без cluster/network:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover \
  -s environments/pz/kubernetes/panel-updater -p 'test_updater.py' -v
```
