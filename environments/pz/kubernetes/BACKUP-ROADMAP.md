# План: пять проверенных копий в S3 и отдельный диск данных

Документ задаёт требования и порядок внедрения. Устройство реализации,
обязательные проверки перед применением и ссылки на код собраны в
[описании реализации](backup/IMPLEMENTATION-20260930.md).
Фактические параметры окружения, журнал rollout, результаты production-проверок
и измерения времени хранятся в отдельном закрытом отчёте оператора.

Локальный backup suite: 229 tests passed без skipped, включая настоящий rsync.
Эти проверки подтверждают поведение кода; решение о применении требует
инвентаризации окружения, просмотра плана и выполнения приведённых ниже gates.

Цель — иметь вне VM пять последних согласованных, полностью проверенных
снимков, из которых можно восстановить игровой мир и необходимую конфигурацию.
Ниже сохранён исходный порядок работ. Конкретные размеры дисков, расписание,
бюджет, допустимый простой и параметры хранилища выбираются для окружения
до применения. Сам документ не запускает никаких действий.

## Исходное состояние

- Игра — `zomboid/zomboid-0`, StatefulSet `OnDelete`, один экземпляр. Runtime
  получает SIGTERM, отправляет RCON `save`, затем `quit`, при недоступном RCON
  использует stdin. Kubernetes даёт 300 секунд. Для подтверждения чистого
  завершения нужны exit 0 и отсутствие игрового процесса; исчезновения pod
  недостаточно. При replicas=1 завершение процесса или удаление pod запускает
  игру снова. Источники: [game.py](../runtime/game/game.py),
  [правила обслуживания](README.md#обслуживание-и-откат).
- Панель отдельно пишет свои данные и имеет доступ на запись к `/zomboid`.
  Её автообновление тоже пишет данные. Для согласованного снимка нужно
  приостановить updater, дождаться завершения его Jobs/Pods, проверить
  терминальный journal и остановить панель вместе с игрой.
- Встроенные ZIP в `/zomboid/backups/startup` полезны для локального отката,
  но находятся на той же VM. Неудачные старты уже приводили к ротации истории
  и пустым ZIP. Их количество и наличие не доказывают целостность или полноту
  нового off-host backup. Имеющийся архив миграции в
  `/var/backups/pz-k3s-20260930/` и `verified.json` — отдельная точка восстановления,
  а не внедрённое регулярное расписание.
- По зафиксированной конфигурации `storage/` данные PZ, Steam, панели и её
  логов разделяют ext4 26 GiB: `/srv/pz-storage/zomboid`. Это loop-файл
  `/var/lib/pz-volumes/zomboid.ext4` на корневом SSD. Edge и observability
  имеют собственные loop-ФС, но тот же физический диск. Legacy-пути
  `/opt/pz-stack/data/*` — ссылки на эти mounts. Подготовленный рост 26 → 50 GiB
  описан в [storage-growth](storage-growth/README.md); перед новым внедрением
  фактическое состояние нужно перечитать, не считать подготовку применением.

## Что входит в снимок

Первый шаг реализации — перечень данных и зависимостей восстановления с
размерами, числом файлов, владельцами и источниками записи. Базовый охват:
мир и персонажи, игровые настройки/БД, серверные моды и собственные скрипты,
данные панели и версия её схемы. Для `/zomboid` начать с полного перечня,
а исключения подтверждать отдельно: одних `Saves` может быть недостаточно.

Снимок сопровождается manifest: UTC-время, уникальный ID, имя мира, версия
PZ/Steam build, перечень Workshop/mod IDs и доступные версии/хэши, digest
игрового и панельного образов, revision инфраструктуры, список включённых и
исключённых путей, размеры и SHA256 файлов, numeric UID/GID, режимы, ссылки,
ACL/xattrs при наличии. Manifest не публикуется открыто: пути и настройки
могут содержать приватные сведения.

Не включать рекурсивно spool и предыдущие архивы. Встроенные startup ZIP,
логи и map-cache можно исключить только после проверки, что они производные
и все первичные данные включены. Бинарники PZ/модов нельзя автоматически
считать всегда повторно скачиваемыми в прежней версии: сначала проверить
восстановление точного build. Недоступные для повторного получения артефакты
сохранять вместе со снимком либо в отдельном защищённом архиве версий.

Секреты, ключи и настройки восстановления хранить зашифрованно. Нужно заранее
решить, входят ли они в этот комплект или восстанавливаются из отдельного
хранилища секретов. Только список имён Kubernetes Secrets не восстанавливает
их значения. Terraform state и старый архив миграции не смешивать с регулярной
ротацией игрового мира.

## Согласованная копия и ограниченное временное место

Предлагаемый первый вариант — один coordinator на VM, запускаемый systemd
timer, с постоянным журналом и блокировкой обслуживания. Задача продолжает
работать при потере SSH; повторное подключение читает её состояние и не
запускает вторую копию. Согласовать блокировку с Terraform deploy, updater,
миграциями/ростом storage и ручным обслуживанием. `Forbid` или локальный lock
одной программы сам по себе не останавливает другие инструменты.

1. Проверить mount UUID, свободные блоки и inode на данных, spool и `/`,
   отсутствие других писателей/задач и достаточность временного бюджета.
   Записать исходные replicas, UID игры и состояние updater. Если игра уже
   намеренно остановлена, backup не должен запускать её после завершения.
2. Приостановить updater и дождаться отсутствия его активных и terminating
   pod; нет незавершённого journal. Остановить панель и игру через replicas=0,
   дождаться штатного save/quit, exit 0 и отсутствия pod/процесса. При timeout,
   OOM, exit 137 или неизвестном исходе не маркировать backup согласованным;
   сохранить диагностику и остановиться для разбора без force-kill.
3. В отдельный каталог spool `<id>.partial` скопировать только согласованный
   набор с сохранением метаданных. Проверить копию по SHA256 и перечню файлов
   при всё ещё остановленных писателях. Обработать ошибки чтения, исчезнувшие
   файлы и запрещённые ссылки как отказ. Записать manifest через временный
   файл, fsync и rename; проверить его повторным чтением. Staging после этого
   неизменяем для последующих фаз задачи.
4. Вернуть приложения в записанное исходное состояние. Восстановить расписание
   updater только после проверки его journal и отсутствия конфликтующих работ.
   Не ждать сети S3, удерживая игровой сервер выключенным: упаковка и upload
   работают с уже проверенной staging-копией. Это требует места для staging.
5. Создать архив в spool с ограничением CPU/I/O/RAM, потоковым SHA256 и полным
   проходом проверки архива/файлов. Переименовать завершённый файл только после
   fsync. После публикации и readback в S3 освободить ровно принадлежащие этой
   задаче временные файлы; активные данные и ручные backups не затрагивать.

Сам по себе RCON `save` не останавливает последующие записи игры. Обычный
live `tar`/`rsync`, копия подключённого `.ext4` и скачивание ZIP в момент его
создания не принимаются как согласованный снимок.

Spool предлагается разместить на отдельной ограниченной ФС, например
`/srv/pz-backup-spool`; конкретные размер и устройство выбрать после inventory.
Для этого алгоритма бюджет должен покрывать **staging + готовый архив +
метаданные + запас**, включая несжатые или плохо сжимаемые файлы. Полный GET
из S3 проверять потоком без второй локальной копии. Одновременно допускается
одна задача. Если предыдущая не завершена и места недостаточно, новая не
начинается; журнал отказа и возраст последней копии отправляются в мониторинг.
Нельзя ради нового запуска удалять единственную ещё не отправленную копию.
Квота PVC сама по себе не ограничивает расход файловой системы.
Игровой лимит `ephemeral-storage=3Gi` остаётся бюджетом его временных файлов;
полный backup не должен создаваться в writable layer или `/tmp` игрового pod.

Более короткий простой можно получить отдельным проектом через снимок
подходящего диска/ФС после остановки писателей. Это не возможность текущего
plain ext4 «по умолчанию». Для cloud snapshot нужны документированный момент
фиксации и надёжный thaw/recovery; filesystem freeze не заменяет завершение
записей приложения. [Порядок snapshots Yandex Compute](https://yandex.cloud/ru/docs/compute/operations/disk-control/create-snapshot).

## Публикация в S3 и пять последних успешных снимков

Предварительный выбор — приватный bucket Yandex Object Storage в используемом
облаке; конкретные bucket, регион, storage class, шифрование и бюджет пока не
выбраны. Пример логической структуры, не реальные созданные ресурсы:

```text
pz/<environment>/<snapshot-id>/payload.tar.zst
pz/<environment>/<snapshot-id>/manifest.json
pz/<environment>/<snapshot-id>/COMMITTED.json
```

Каждый ID уникален; успешные данные не перезаписываются. Сначала загрузить
payload, затем полностью скачать его потоком и сравнить длину и SHA256 с
локальным архивом. Проверить manifest отдельным GET. Не считать HTTP success,
HEAD, ETag или собственный metadata-параметр `sha256` доказательством совпадения
скачанных байтов. Возможности SDK/checksum и conditional PUT проверить именно
для выбранного S3 endpoint. Yandex поддерживает multipart и условия записи;
незавершённые части нужно отдельно отменять/очищать.
[Multipart API](https://yandex.cloud/en/docs/storage/s3/api-ref/multipart),
[условия загрузки](https://yandex.cloud/en/docs/storage/operations/objects/upload).

Последним записывается и перечитывается `COMMITTED.json`: ID, ссылки на точные
objects/версии, SHA256 manifest и payload, размеры, время согласованной копии
и успешной удалённой проверки. Это прикладной протокол завершения, а не
транзакция S3 над несколькими объектами. Restore и retention принимают только
полные согласованные комплекты с корректным marker. После неопределённого
результата запроса сначала перечитать известный ключ и сравнить содержимое;
не создавать новый ID и не удалять прежнюю копию вслепую.

Retainer после подтверждённого commit выбирает пять новейших проверенных
снимков по зафиксированному времени снимка и стабильному ID. Затем проверяет
наличие их объектов/версий и только после этого удаляет более старые комплекты
по точным ключам. При ошибке чтения, неполном listing или неоднозначном
состоянии удаление запрещается. Публикация и retention сериализованы; журнал
удалений допускает безопасное продолжение после сбоя. Пока успешных снимков
меньше пяти, ничего из них не удаляется. В процессе может временно храниться
шесть и более комплектов; ошибка очистки оставляет лишние, а не сокращает
число пригодных копий.

«Пять последних успешных снимков» — пять комплектов восстановления, не пять
отдельных объектов и не пять последних запусков задачи. Пять неудачных
backup не должны вытеснить ни одной исправной копии. Возрастная lifecycle
политика не заменяет этот алгоритм; её использовать для отдельно обозначенных
незавершённых multipart/staging-объектов. Настройки bucket versioning и удаления
старых версий входят в расчёт расходов. [Lifecycle](https://yandex.cloud/en/docs/storage/concepts/lifecycles).

Object Lock — отдельное решение: он защищает версии от удаления, включая
lifecycle, но может намеренно оставлять больше пяти комплектов до истечения
срока. Не включать его молча с обещанием «строго пять объектов».
[Object Lock](https://yandex.cloud/en/docs/storage/concepts/object-lock).
Архив миграции исключить из retainer до отдельного решения владельца.

## Права, секреты и наблюдаемость

Разделить исполнение на получение согласованной локальной копии, загрузку
и очистку старых удалённых копий. Uploader читает только готовый spool; он
не получает право удалять успешные снимки. Retainer имеет удаление только
backup-prefix данного окружения, restore-учётная запись — только чтение.
Coordinator получает строго необходимые операции над именованными игровым
StatefulSet, панелью и updater; в доверенном host helper остаётся доступ к
фиксированным каталогам и журналу. Права uploader не должны позволять
управление Kubernetes или cloud VM.

Bucket policy ограничивает principal, object-prefix и ListBucket prefix;
исключить публичный доступ и административные права на весь folder. В итоговом
IAM fixture проверить нужные GET/PUT/multipart и запрещённые чужие prefixes,
DeleteBucket, смену policy и удаление committed uploader-ом.
[Модель bucket policy](https://yandex.cloud/en/docs/storage/security/policy).
Ключи выдаются отдельно от обычного Git-кода, не выводятся в логах и не
публикуются в CI artifacts; способ доставки и ротации выбрать до реализации.
Учесть, что создание постоянного ключа через Terraform может поместить секрет
в state: доступ к state — доступ к секретам. Ключ расшифрования должен
восстанавливаться после полной потери VM.

В Monium нужны возраст последнего committed backup относительно выбранного
RPO, длительность остановки/копирования/upload, размер, число проверенных
снимков, ошибки SHA/restore, свободные блоки/inode spool и данных, незавершённые
multipart, состояние задачи после reboot. Логи содержат ID и фазы, без
паролей, токенов, содержимого saves и имён игроков. Канал уведомлений выбирает
владелец. Перезапуск приложения после копирования не скрывает неудачу upload.

## Отдельный диск данных

Текущий loop ext4 ограничивает вместимость окружения, но резервирует данные
на том же root SSD: его заполнение/потеря затрагивает и ОС, и мир. Рост loop
26 → 50 GiB эту зависимость не устраняет. Целевой вариант — отдельный cloud
block disk для данных PZ с собственным ext4 и UUID; spool имеет отдельный
ограниченный бюджет, предпочтительно отдельное устройство при достаточном
бюджете. Spool на одном диске с миром допустим лишь как временный компромисс:
разделы/квоты ограничивают заполнение, но не отделяют отказ устройства и I/O.
Прикреплённый второй диск не заменяет off-host S3.

Миграция диска — самостоятельное окно обслуживания после успешного S3 backup
и restore drill: создать/подключить явно выбранный новый диск, проверить его
ID и отсутствие данных, подготовить ФС, остановить всех писателей, скопировать
с метаданными и сверить SHA256. Сохранить привычные пути PV/legacy symlinks,
переключить mount по UUID, обновить fstab и systemd `RequiresMountsFor`/проверку
mountpoint, чтобы отсутствие диска не приводило к записи в пустой каталог `/`.
Проверить UID/GID, права, вместимость, запуск и план без изменений. Существующий
loop/state не форматировать и не переписывать как будто это первая миграция.
[Подключение диска](https://yandex.cloud/en/docs/compute/operations/vm-control/vm-attach-disk).

Старую копию сохранить на согласованный срок. После записей игры на новом
диске откат mount на старую копию потеряет новые сохранения: сначала вновь
остановить игру, сделать свежий backup и перенести актуальные данные назад.
Автоматического удаления старого диска/loop или `destroy` в migration helper
не предусматривать; Terraform-диски/PV защищать `prevent_destroy`/`Retain`.

## Проверка восстановления и этапы GitHub

До включения retention выполнить полный restore из S3 на пустую изолированную
ФС/VM: marker и SHA, безопасное извлечение без выхода за каталог, типы файлов,
права и полнота; затем нужные версии игры/модов, приватный запуск, RCON health
и проверка загруженного мира. Тестовый сервер не подключается к production PV,
публичным игровым портам или production-интеграциям панели/Discord. Измерить
RTO и сохранить обезличенный отчёт. После изменения формата/mods/runtime и
периодически повторять drill; его частоту выбрать вместе с RPO. Совпадение
SHA подтверждает байты, но только restore drill проверяет пригодность комплекта.

Целевой репозиторий — [updatingspace/infra](https://github.com/updatingspace/infra),
локальная рабочая копия `infra-repo`, ветка `chore/pz-k3s-iac`. Выполнен локальный
перенос `infrastructure/` в `infra-repo/environments/pz` с совместимой ссылкой
по старому пути. Старые Swarm stack/configs/workflow размещены в `legacy/swarm`,
а Compose — в `environments/pz/legacy/compose/{stack,collector}`.
Это локальная организация кода, не подтверждение push/merge или deployment.
Относительные ссылки внутри переносимого дерева должны продолжить работать.

Этапы интеграции:

1. Проверить visibility, доступы и порядок review в указанном репозитории.
   Переносить только проверенный код/шаблоны; исключить `.env`, private tfvars,
   state/plan, kubeconfig, ключи, архивы и пользовательские данные. Сопоставить
   имеющиеся cloud/storage/workloads states без повторного создания ресурсов.
   Проверить совместимую ссылку, пути deploy/CI и отсутствие активного workflow,
   продолжающего раскатку архивированного Swarm. State не переносить в Git.
2. Отдельным PR описать Terraform root для bucket/IAM/шифрования и отдельного
   диска, версии providers, `prevent_destroy`, способ защищённого state с
   блокировкой и импорт уже существующих ресурсов. Проверить план на отсутствие
   пересоздания VM, удаления storage и изменения игровых данных.
3. Следующим PR добавить coordinator/uploader/retainer, journal, расписание
   первоначально disabled, лимиты ресурсов и мониторинг. В CI: fmt/validate,
   provider mocks и сценарии обрыва SSH/reboot, заполнения spool, повреждения
   архива, неполной загрузки, ambiguous commit, отказа retention, остановленной
   заранее игры, конкуренции updater и сохранения пяти исправных копий.
4. PR проходит проверки без production-секретов; применять только просмотренный
   сохранённый план из доверенного окружения. Для GitHub Actions рассмотреть
   OIDC с узкой привязкой repository/ветки/environment вместо постоянного
   облачного ключа; поддержку конкретных API/SDK проверить отдельно.
   [Yandex Workload Identity Federation](https://yandex.cloud/en/docs/iam/operations/wlif/setup-wlif).
5. Вручную выполнить один backup и полный restore drill, проверить прежние
   production-данные и время простоя. Затем включить расписание; retention
   включить после успешного drill и проверить накопление первых пяти снимков.
   Миграцию на отдельный диск проводить отдельным reviewed plan и проверять
   независимым отчётом. Не запускать произвольный PR-код на production VM.

и способ доступа CI.
