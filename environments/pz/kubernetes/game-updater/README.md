# Обновления игрового сервера

`pz-game-update.timer` проверяет Steam public (app 380870) через час после
завершения предыдущего запуска, с разбросом до двух минут. Первый запуск —
через 15 минут после загрузки VM, либо сразу при установке на работающую VM.
Проверка не обновляет игру. При совпадении build ID сервер продолжает работу.
Автоматический переход на меньший build ID запрещён.
При наличии игроков новая версия откладывается до следующей проверки.
Число игроков повторно проверяется непосредственно перед остановкой.

При новой сборке host controller берёт общий maintenance lock, приостанавливает
updater панели и использует существующий backup coordinator: SIGTERM вызывает
`save` и `quit`, проверяются exit 0 и отсутствие процессов, создаётся полный
снимок мира, конфигурации и прежних файлов игры с проверкой содержимого.
Копия на spool остаётся доступна при неудачном обновлении. Это добавляет примерно
20 минут простоя на текущем размере мира; шифрование и выгрузка идут после старта.

SteamCMD запускается в отдельном Kubernetes Job без API token, Secret и тома мира,
под UID 1000, с лимитом 1.8 CPU / 2 GiB RAM. Он явно выбирает `public`.
Job использует тот же runtime flock, что игра. После exit 0 проверяются
сообщение Steam об успехе и точный build ID; Job удаляется перед запуском игры.
Готовность проверяется до 30 минут через Kubernetes и RCON. Затем возвращаются
панель, collector и расписание обновления панели; snapshot шифруется и передаётся
существующему проверяемому S3 uploader с прежней retention-политикой.

Неудача после изменения файлов оставляет durable `game_update_*` journal,
блокирующий новый backup и Terraform deployment. Автоматического отката мира
нет: новая версия уже могла мигрировать сейв. Ошибку разбирает оператор.
При неудачном запуске кандидат может оставаться запущенным для диагностики;
панель и её updater не возобновляются до подтверждённой готовности.

## Доставка

1. `python3 ../deploy.py sync`, затем reviewed `plan workloads` / `apply workloads`
   создают сетевую политику для maintenance Job.
2. В этом каталоге: `terraform init`, `terraform plan -out=reviewed.tfplan`,
   `terraform apply reviewed.tfplan`. State локальный, игнорируется Git.
   Адаптер устанавливает свои три файла, обновляет read-only exporter метрик
   для учёта нового service и включает timer через SSH. Действующий backup
   coordinator не переустанавливается. Ошибка service попадает в существующие
   метрики `pz_backup_current_job_failed` с `job="game_update"`.

На VM:

```sh
sudo systemctl start --no-block pz-game-update.service
sudo systemctl list-timers pz-game-update.timer
sudo journalctl -u pz-game-update.service
sudo cat /var/lib/pz-backup/game-update.json
sudo python3 /opt/pz-game-update/controller.py --check
```

Один systemd service исключает собственные параллельные запуски. Общий flock
исключает одновременную миграцию дисков, backup и apply. Для операторского
обновления с игроками существует `--force-players`; timer этот флаг не использует.
Между последней проверкой игроков и остановкой остаётся короткое окно нового
подключения; такой игрок также завершится штатным save/quit.

Не запускать Steam update из панели: её игровой том намеренно доступен только
для чтения, а обновления координируются здесь с backup и Kubernetes.
