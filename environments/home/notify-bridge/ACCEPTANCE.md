## Проверки

- 9 Go-тестов с race detector, `go vet`: успешно.
- 7 Python-тестов: конвертация/отсечение неподдерживаемых подписок,
  переключение на проверенный узел, сохранение рабочего конфига при отказе
  подписки, внеочередное обновление протухших ключей, границы манифестов.
- Python syntax compile и Node syntax check: успешно.
- DNS Telegram совпал с независимым DoH; прямой IPv4 и варианты ByeDPI
  не дали соединения. Через Xray/VLESS/XHTTP HTTPS Telegram вернул 302,
  проверка сертификата включена.
- Kuma: notification ID 1, имя Notify Bridge, привязана к 21 активной
  проверке. Ранее выключенные проверки остались выключенными.
- AM: webhook добавлен к существующему email receiver; amtool check-config
  прошёл. Синтетическое событие через настоящий `/api/v2/alerts` доставлено
  в Telegram. Обработано нажатие «Принял».
- Prometheus: job `notify-bridge` имеет health=up, 10 новых alert rules имеют
  health=ok. Предыдущие группы/маршруты сохранены.
- Отказный сценарий: egress масштабирован до 0; синтетический Kuma DOWN
  принят в очередь; bridge перезапущен; запись осталась недоставленной и
  сохранила ID. После возврата egress до 1 сообщение доставлено, UP обновил
  карточку и отправил отдельное восстановление. Рабочие сервисы не выключались.
- Прокси вживую отверг CONNECT к example.com; webhook без ключа вернул 401.
- SQLite `integrity_check=ok`; online backup с собственной integrity-проверкой
  создан без остановки bridge. Полное восстановление на другой VM не выполнялось.
- Четыре systemd timer включены. VPN, Kuma reconciliation, health и backup
  выполнены с `Result=success`, `ExecMainStatus=0`.
- Токен Telegram введён владельцем непосредственно на VM; одноразовая
  привязка личного чата пройдена, кнопки подтверждены через сохранённый ack.
  Факт отображения push на заблокированном экране iPhone отдельно не проверен.

Итоговая сверка: все три синтетических инцидента закрыты; их карточки и
восстановления приняты Telegram. Очередь пуста. Девять правил канала/ID
неактивны; `IDBackupRecoveryPending` находится в pending из-за сохранённого
старого resume-marker. Публичный и origin `/readyz` ID проверены curl: HTTP 200.

## Ограничения и оставшаяся работа

- Сбой всей VM/её интернета требует внешнего наблюдателя.
- Возобновление истёкшей платной подписки или замена отозванной ссылки
  требуют владельца; автоматическое обновление касается доступного feed.
- Первичный успешный узел проверен вживую. Автоматический переход между
  разными VPN-узлами проверен тестами; реальный отказ внешнего узла не вызывался.
- Недоставленная очередь не потерялась при рестарте; при неопределённом результате
  Telegram sendMessage редкий дубль всё же возможен.
- ID backup resume-marker всё ещё существует. Новый алерт обнаруживает это,
  но исправление старого backup.py и полноценный backup/restore ID не входят
  в проверенное изменение notify-bridge. HTTP-восстановление ID не является
  доказательством исправления его backup lifecycle.
- На момент первичной приёмки изменения были локальными в `codex/notify-bridge`;
  публикация выполняется отдельно в PR #18 от актуального `master`.
